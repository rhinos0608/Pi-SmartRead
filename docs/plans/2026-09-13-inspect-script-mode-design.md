# inspect script-mode design

**Date:** 2026-09-13
**Status:** Draft — reviewer hardening pass incorporated; pending QuickJS spike
**Owner:** Pi

## Goal
Let `inspect` accept a bounded, read-only JS script that composes several retrieval/graph/LSP operations (grep, read, file/dir inspect, LSP navigation, graph impact/deadCode/callgraph) inside one tool call, instead of forcing N sequential tool round trips.

## Non-goals
- No write/mutate host bindings, ever. Script mode cannot call `edit`/`write`/`patch` — read-only by construction, not by policy check.
- No general Node access inside the sandbox (no `fs`, `net`, `process`, `require`).
- No new `inspect` output modes for existing path-based dispatch — script mode is a fully separate branch, not a third `InspectV4Mode` value.
- No protocol version bump — script mode must fit inside `@rhinos0608/pi-workspace-protocol` v3 as-is (confirmed feasible, see Evidence section).

## Context
- Current `inspect` dispatches by `statSync(path)`: directory → repo map, file → structural facts. Schema in `src/inspect/inspect-tool.ts`, dispatch in `src/inspect/inspect.ts`.
- Evidence contract: every tool result's `details.workspaceEvidence` is a `WorkspaceEvidenceEnvelope` (schema v3, `@rhinos0608/pi-workspace-protocol`). `mode` is a closed, runtime-validated enum: `"path" | "query" | "symbol" | "map"` (`contract.ts` `validateInspectionEnvelope`). `query`/`symbol`/`map` already permit zero resources; `path` (or omitted mode) requires ≥1.
- `resourceIdFor({kind, canonicalPath, range})` hashes kind+path+range — a full-file read and a range/search-match hit on the same path get *different* resourceIds. This means naive union-dedupe-by-resourceId across many calls is already correct; no "strongest coverage wins" merge pass is needed.
- `src/evidence/read-many-evidence.ts`'s `buildBatchWorkspaceEvidence()` already solves "merge N per-call envelopes into one batch envelope" for `read({ paths: [...] })`. It hardcodes `mode: "path"`.
- `executeInspectV4()` (`src/inspect/inspect.ts`) and grep's compute layer already build a complete `WorkspaceEvidenceEnvelope` per call, independent of the tool wrapper's `resolver.publishInspection()` side effect. The *-tool.ts wrappers only relay + publish that envelope once per execute() call — publishing is tied to a single outer `pi.tool_result.*` event, not to how many internal ops ran.
- No sandbox dependency exists in this repo today (`package.json` has none of vm2/isolated-vm/quickjs/starlark).

## Recommended approach
QuickJS via `quickjs-emscripten` (justjake, `@jitl/*` variants), WASM-isolated interpreter, no Node builtins exposed, host functions injected as the *only* API surface. Read-only host API removes the worst blast-radius concern (no corrupted repo state possible — worst case is wasted CPU/time inside a bounded run).

Host API: fine-grained typed namespaced functions mirroring existing `InspectV4Input` fields 1:1 — no new capability, only a new calling convention:
- `grep(pattern, opts)`
- `read(path, opts)`
- `inspectFile(path, opts)` / `inspectDir(path, opts)`
- `lsp.definition/references/implementation/hover/documentSymbols/workspaceSymbols/prepareCallHierarchy/incomingCalls/outgoingCalls(...)`
- `graph.impact/deadCode/callGraph/hotspots/routes/diff/clusters/layers/boundaries(...)`

Rejected: generic `call(op, args)` dispatcher — same power, worse ergonomics, no benefit since the op set is closed and small (matches Anthropic/Cloudflare code-exec-with-MCP precedent of exposing typed per-tool functions, not one generic invoker).

## Alternatives considered
1. **Declarative JSON step-plan (no eval)** — safest/most staticaly auditable, but no loops/branches without hand-adding step types one by one; less expressive for genuinely exploratory multi-hop investigation. Rejected per explicit user direction (read-only removes the main reason to prefer this).
2. **isolated-vm** — true V8 isolate, but native addon (node-gyp build), Node-version lockstep, "maintenance mode" upstream, and a real escape surface if `Reference`/`ExternalCopy` misused. Rejected: not worth the operational risk for a read-only use case where QuickJS's weaker JS-feature fidelity is a non-issue.
3. **Starlark** — deterministic/hermetic by design (ideal semantics), but no mature JS binding (npm `starlark` is a dead v0.0.0 placeholder; real path is a Go/Rust sidecar process). Rejected: too much integration cost for an in-process TS tool.
4. **vm2 / bare node:vm** — excluded outright. vm2 has a history of sandbox escapes (CVE-2026-22709, CVSS 9.8) and is not a real security boundary; `node:vm` was never a security boundary.

## Reference repo evaluated: mksglu/context-mode (not adopted)

Checked as a possible architecture reference on 2026-09-13. Verified directly against the repo's `package.json` (dependencies, license) and `README.md` (problem statement, mechanism) — not just the repo name/description.

**Conclusion: different pattern, not applicable as a sandbox/host-binding template.** `context-mode` solves context-*window* exhaustion (raw tool output flooding the model's context), not tool-call composition. Its "Think in Code" feature (`ctx_execute`) looks superficially similar — "the LLM writes a script instead of calling N tools" — but the mechanism is an OS **subprocess** running a full language runtime (JS/TS/Python/shell/Ruby/Go/Rust/etc., preferring Bun) with real `fs`/`network`/`require` access, gated only by a deny-list firewall (dangerous shell commands, env-var denylist, project-path boundary check) — not an in-process typed-capability sandbox. There is no QuickJS/isolated-vm/vm2/any embedded JS engine in its dependency tree (confirmed: `package.json` deps are `@modelcontextprotocol/sdk`, `better-sqlite3`, `zod`, `turndown`, etc. — no sandbox library). There are no typed per-operation host bindings comparable to our `grep`/`read`/`lsp.*`/`graph.*` — guest code gets a full runtime and calls real APIs directly, then only `console.log` output returns to the model.

This is the opposite security posture from ours: we start from zero capability and add back a small typed read-only surface (§1 in Security hardening); `context-mode` starts from full capability and subtracts via a firewall/denylist. Do not import its threat model, sandbox choice, or host-binding shape.

Worth noting as precedent (not adopted verbatim, just consistent with decisions already made in this doc): its output-truncation/echo-cap posture (full code always executes; only the *echoed* command/code text shown back to the model is capped) matches the spirit of our §5 bounded call log (log is for audit visibility, not a capability gate) — and its documented reasoning for *not* imposing a fixed server-side execution timer (a fixed timer broke real long-running builds in their case, per their issue history) is a useful caution but does not change our design: our script runs are bounded exploratory read-only investigations on the order of seconds, not arbitrary builds, so the §2 host-side hard deadline stays as designed.

License flag: `Elastic-2.0` (source-available, not OSI-approved open source) — moot here since we are not vendoring or depending on this repo, only using it as a design reference.

### Adopted: tool-description discipline (context-mode ADR-0002), not the hook/injection layer

Separately investigated `context-mode`'s routing-*enforcement* stack (2026-09-13) — how it gets a model to actually prefer its tools over raw Read/Bash/Grep. Verified directly against `docs/adr/0002-tool-description-style.md`, `hooks/routing-block.mjs`, and `configs/opencode/AGENTS.md`. Their stack has three tiers: (1) a static per-platform instruction file (`AGENTS.md`/`.mdc`) copied into the consumer's project, (2) a `SessionStart`-injected system-prompt "routing block" (`hooks/routing-block.mjs`) plus `PreToolUse` hooks that can `deny`/`modify`/inject `context` on specific tool calls, (3) the MCP tool descriptions themselves.

**Correction (supersedes the first pass above): we are NOT MCP-only.** Pi-SmartRead's primary mode is a native Pi extension (`src/index.ts` `export default async function (pi: ExtensionAPI)`); MCP is one adapter among several, not the ceiling on what's available. Verified directly against this repo's own source, not inferred: we already have a `SessionStart`-equivalent (`pi.on("session_start", ...)`) and a real system-prompt injection point (`pi.on("before_agent_start", ...)` in `src/hook.ts`, which literally returns `{ systemPrompt: additions.join("\n") }` — already used today to inject the repo map, git context, and a `## SmartRead Tool Guide` block via `renderSmartReadToolGuide()` in `src/runtime/tool-guidance.ts`). We also already have a `PreToolUse`-equivalent (`pi.on("tool_call", ...)`) and a `PostToolUse`-equivalent (`pi.on("tool_result", ...)`), both wired in `src/index.ts` through `handleToolCall`/`handleToolResult` in `src/extension-result-pipeline.ts`. So per context-mode's own taxonomy, we sit in their **hook-capable tier** (their measured ~98% compliance ceiling), not the ~60% MCP-only fallback tier — the first-pass analysis above was wrong about our own architecture and is retained only so the correction stays visible, not silently dropped.

**Concretely, this repo already has a working, shipped mechanism that is the direct analog of context-mode's periodic/`guidanceOnce` nudge — the doom-loop detector (`src/runtime/doom-loop.ts` + `src/runtime/doom-loop-suggestions.ts`).** It runs on the existing `tool_result` hook (`injectDoomLoopWarning`) and already fires exactly on the pattern script mode exists to replace: `read-file-loop` triggers when ≥12 context-gathering calls (`grep`/`read`/`inspect` are literally in its `READ_LIKE_TOOLS`/`CONTEXT_GATHERING_TOOLS` sets) spanning more than one tool kind occur within a 15-call window with no interleaved "progress" tool (`bash`/`edit`/`write`/`graph_mutate`) — i.e. exactly a multi-hop grep→read→grep→inspect investigative chase. `action-stagnation` similarly fires at ≥16 same-tool calls (grep/read/inspect are `HIGH_VOLUME_TOOLS`, so they get the higher `READ_LIKE_STAGNATION_THRESHOLD`, not the lower 8-call generic threshold) with low input diversity. When either fires, `injectDoomLoopWarning` appends a rendered warning — including per-tool suggestion bullets pulled from the `SUGGESTIONS` table in `doom-loop-suggestions.ts` — directly into that tool call's own result text. This is a real, already-tested, already-shipped equivalent to context-mode's runtime nudge tier, just triggered by a repetition/stagnation heuristic instead of a fixed per-N-calls counter.

**Correction (user feedback, 2026-09-13): doom-loop nudges are a reactive backstop, not primary guidance, and are insufficient alone.** `read-file-loop`/`action-stagnation` only fire *after* ≥12–16 calls' worth of exactly the wasteful pattern script mode is meant to prevent has already happened — that is failure-recovery, not steering. Adding a `SUGGESTIONS` entry (kept below, still worth doing as a cheap backstop for whatever cases still slip through) is not sufficient on its own. Two additional, proactive channels are needed, seen *before* a model ever starts a wasteful multi-hop chase rather than after:

1. **Cross-reference script mode from each standalone tool's own description**, not just `script`'s own description. `grep`'s, `read`'s, and `inspect`'s descriptions (`GREP_DESCRIPTION` in `src/search/grep-tool.ts`, the inline description in `createExtendedReadTool` in `src/hook.ts`, `INSPECT_V4_DESCRIPTION` in `src/inspect/inspect-tool.ts`) are read by the model at *every* tool-selection decision, not just when it's already stuck — this is the proactive equivalent of context-mode's `WHEN NOT:` cross-tool disambiguation bullets. Add one `WHEN NOT`-style bullet to each (per the same ADR-0002 discipline below: affirmative framing, no forbidding tokens): e.g. grep's description gains a line to the effect of "chasing a multi-hop lead across several dependent calls (grep → read → grep → inspect) → consider `inspect { script }` to compose the chase in one call." This is a follow-up documentation-only change to three existing description strings, not a new mechanism — low-risk, and it is the primary lever, with the doom-loop `SUGGESTIONS` entry as its reactive backstop for cases where the model didn't act on the proactive cue.

2. **Author a dedicated Pi Skill teaching the pattern**, discoverable via this repo's own `skill` tool (`src/runtime/skill-tool.ts`). Verified directly against `discoverRoots()` in that file: skills are resolved from `~/.pi/agent/skills/` (global), `<ancestor>/.pi/skills` and `<ancestor>/.agents/skills` (project), and a package-root `skills/` dir or a `package.json` `pi.skills` array, walking up from the session's `cwd`. A `SKILL.md` (frontmatter `name`+`description`, procedural body) teaching "when investigating multi-hop code relationships — symbol → references → impact, or a chain of dependent lookups — prefer `inspect { script }` over N sequential grep/read/inspect calls" is genuinely additive: it is discovered the same way every other process skill in this environment already is (via `skill({action:"search"})` / the `using-superpowers`-style router), and unlike a routing file it does not require write access to a consumer's project. **Distribution constraint, stated honestly rather than glossed over:** a `skills/` dir at this package's own root is auto-discovered only when the session's `cwd` is at-or-under this repo (i.e. while developing Pi-SmartRead itself) — for an arbitrary *consumer* project depending on Pi-SmartRead as an installed extension, the skill only becomes discoverable if it is separately installed to that user's `~/.pi/agent/skills/` (global, works everywhere) or that consumer project explicitly declares it. This is the same practical reach limitation context-mode's own instruction-file tier has (their file must be copied into each consuming project too) — script mode's Skill should still be authored and shipped in this repo (worth it for this repo's own dev sessions and for global-install users), but its per-consumer-project reach is a packaging/distribution decision separate from this design doc, not something to overstate here. Keep the SKILL.md itself compact — pointer-style (WHEN/WHEN NOT + one canonical example + pointer to this design doc), not a manual; the model pulls the full text only when the skill router deems it relevant. And auto-surface it while the extension is active: the one-line script-mode pointer already planned for `TOOL_GUIDE_LINES` (auto-injected every session via the existing `before_agent_start` hook — no skill lookup, no opt-in needed) doubles as the skill's auto-inject, naming the skill so the model can pull it on demand.

**Adopted addition (both proactive channels above, plus the reactive backstop; low-risk, no new hook plumbing, follow-up work item, not blocking script-mode implementation):** add a script-mode suggestion entry to the existing `SUGGESTIONS` table for `grep`, `read`, and `inspect` (`src/runtime/doom-loop-suggestions.ts`), e.g. `{ text: "if this is a multi-hop chase (grep → read → grep → inspect following a lead), consider inspect { script: ... } to compose the chase in one call", toolHint: "inspect" }` — this reuses the exact existing, tested `consumeDoomLoopWarning`/`injectDoomLoopWarning`/`renderSuggestionBullets` pipeline, zero new hook code, and remains valuable as the backstop for whatever the two proactive channels above miss. Separately, add one short paragraph to `TOOL_GUIDE_LINES` in `src/runtime/tool-guidance.ts` (rendered once per session via the existing `before_agent_start` system-prompt injection) introducing script mode's existence and its `WHEN` shape — this is the direct analog of context-mode's `SessionStart` routing-block teaching-once-per-session role, written in this file's existing plain declarative style (its current lines already avoid `MANDATORY`/`NEVER`/forbidding language, so no ADR-0002-style cleanup is needed there, just an additional line in the same voice).

**Explicitly NOT adopted:** context-mode's `PreToolUse` `deny`/`modify` coercion (hard-blocking or rewriting a competing tool call before it executes). Our existing `tool_call` hook (`handleToolCall`) is passthrough-only today (feeds the doom-loop detector, returns `undefined`) and should stay that way for this feature — denying or rewriting `grep`/`read`/`inspect` calls to force script-mode usage would be a materially larger, riskier behavior change to tools other agents/sessions already depend on, unrelated to shipping script mode itself, and not something to bundle into this design without its own dedicated review.

**Tier 3 (tool description style) is directly transferable and adopted.** ADR-0002 documents an empirically-grounded contract (38 A/B trials × 6 probes on Haiku + Sonnet) for how MCP tool *descriptions* (not system-prompt injection) affect model tool-selection, independent of any hook layer — this is exactly our situation. Adopted rules for the `script` param's description in `src/inspect/inspect-tool.ts` (and worth a pass over the existing `INSPECT_V4_DESCRIPTION`/`GREP_DESCRIPTION` too, as a follow-up, not blocking this feature):
- Structure: `WHEN:` / `WHEN NOT:` / `RETURNS:` / `EXAMPLE:`, in that order, uppercase headers, markdown `- ` bullets only (no numeric/asterisk/emoji bullets), one blank line between sections, one canonical worked example.
- Positive selection cues (`WHEN:`) before negative disambiguation (`WHEN NOT:`) — affirm capability, don't just prohibit.
- Forbidden tokens confirmed to *measurably degrade* selection quality on at least one tested model: `MANDATORY:` (as an opener), `BLOCKED`, `PREFER X OVER Y`, `Do NOT use/read/pull`, `Never use`, `✅`/`❌` emoji bullets. Their root-caused failure mode (PR #654): the single word `"blocked"` in a deny-reason was misread by Opus 4.6 as a safety/network restriction, causing capitulation back to the tool it was supposed to redirect away from — 6/6 → 0/6 after switching to `"redirected"` wording with an affirmative capability statement (`"has full network access"`) instead of a bare negation. Directly relevant to us: our own § Error handling's `"degraded"`/`"unavailable"` status vocabulary (already borrowed from `NavigationStatus`) stays clear of exactly these flagged tokens — no change needed there, but confirms the existing choice was right and should not drift toward `"blocked"`/`"forbidden"` phrasing under future edits.
- Concretely for `script`'s description: `WHEN:` bullets should name the shape that actually benefits — a multi-hop investigation where the next call's arguments depend on the previous call's result (e.g. grep a symbol → LSP references on the hit → graph impact on those files) that would otherwise cost 3+ sequential round trips. `WHEN NOT:` should name the common near-miss — a single lookup answerable by one `grep`/`read`/`inspect` call, or needing to see full prose/file content directly (still use plain `read`, since script mode's return value is a synthesized JSON result, not raw file text). `RETURNS:` should mention the bounded call log (§5) so the model knows it gets visibility into what actually ran, not just an opaque final value.

This is a description-writing constraint to apply when the `script` schema param is actually implemented (roadmap step 6), not a change to make right now — recorded here so it's not lost or re-derived later.

## Design

### Schema (src/inspect/inspect-tool.ts)
New optional top-level param `script: string`. When present:
- `path` becomes optional — used only as the cwd-anchor/default arg for host calls that omit an explicit path.
- All other mode-specific params (`signals`, `mapTokens`, `focus`, `compact`, `callDepth`, `callDirection`, `deadCode`, `impact`, `diff`, `clusters`, `graphSchema`, `hotspots`, `boundaries`, `routes`, `layers`, `navigation`, `diagnostics`) are rejected with the same "Error: inspect param X requires Y" pattern already used by `validateDirOnlyParams`/`validateCrossParams`.
- Dispatch: `executeInspectV4` gains a script branch checked before `resolveInspectV4Mode()`'s stat-based dispatch — script mode never touches the file/dir mode machinery.

### Execution
- Sandbox: one QuickJS context per script call. Hard caps (tune after spike): wall-clock deadline ~3-5s via `shouldInterruptAfterDeadline`, memory 8-16MB via `memoryLimitBytes`, instruction-count interrupt as backstop, host-call count cap ~50/run enforced host-side (not by the interpreter).
- Host bindings call the underlying **compute-layer** functions directly (`executeInspectV4`, grep's `executeGrepQuery`, the LSP inspection provider) — never the registered tool-level wrappers. This is load-bearing: tool wrappers call `resolver.publishInspection()` themselves, and that publish is meant to happen exactly once per real `pi.tool_result.inspect` event. Calling N tool wrappers inside one script would either be wasted redundant publish attempts or invite inspectionId collisions within a single synchronous run.
- Concurrency: `Promise.all` over multiple host calls is supported — QuickJS's own microtask queue resolves pending host promises as they settle; the host-call-count budget bounds fan-out abuse regardless of concurrency.
- Every host call appends `{op, args, envelope}` to an in-run call log (the `envelope` being that call's own already-built per-call `WorkspaceEvidenceEnvelope`).

### Evidence synthesis
After the script returns (or is cut off by a budget), the call log's per-call envelopes get merged with a **generalized** `buildBatchWorkspaceEvidence` (add an optional `mode` param, default `"path"` to preserve read-many's existing behavior; script mode passes `"query"`, matching contract.ts's already-permitted "may legitimately have zero resources" bucket). Dedup-by-resourceId is already correct as-is because `resourceIdFor` hashes kind+path+range — a `search-match` hit and a later `full-file` read of the same path naturally coexist as two distinct resource entries; nothing needs to be "upgraded". The single merged envelope becomes `details.workspaceEvidence` on the one real tool result, and the existing `resolver.publishInspection()` call in `inspect-tool.ts` (already best-effort, already unconditional on `details.workspaceEvidence`) needs no changes.

### Output
Script's returned JS value (JSON-serializable) becomes the structured `details` payload; a rendered text form becomes `contentText`, following existing truncation/byteLength/lineCount conventions in `InspectV4Result`. `console.log` calls inside the script, if exposed, are captured as a side-channel log rather than the primary return value.

### Error handling
Interrupted runs (timeout / step limit / host-call budget / memory limit) return a structured degraded result — following the existing `NavigationStatus`/`DiagnosticsStatus` pattern (`"ok" | "degraded" | "unavailable" | ...` open string union) — not a thrown tool-level error. Script-level JS exceptions are caught and surfaced the same way, with whatever partial call log/envelope had accumulated before the throw still returned (partial evidence is valid evidence — same principle as `read-many`'s "only complete rendered blocks get authority").

## Security hardening (reviewer-required, pre-implementation)

The scripting architecture (A) survived review. These eight points must be resolved in this document before workers start slicing implementation — they are load-bearing, not polish.

### 1. Sandbox threat model — QuickJS/WASM is not itself a security boundary
A read-only host API bounds the *intentional* surface, but must not be read as "QuickJS compromise is harmless." Concretely:
- Pin an exact `quickjs-emscripten` package, version, and lockfile hash — no floating range.
- Freeze the exposed host API object (`Object.freeze` on the bindings object and its namespaces) before injecting it into the guest context, so guest code cannot monkey-patch `grep`/`lsp.*`/`graph.*` mid-run.
- Remove or no-op guest-visible `eval`/`Function` constructor inside the QuickJS global object where the binding layer allows it — script mode has no legitimate use for dynamic code generation from within the sandboxed script itself.
- Keep the Asyncify/host-promise bridge minimal: only the typed host functions below cross the bridge, no generic message-passing channel.
- Spike must include sandbox-escape-oriented fuzzing (malformed host-call args, prototype-pollution attempts via bindings, WASM memory-pressure probes), not just correctness/perf checks.
- Worker-thread or separate-process isolation remains an available *later* hardening layer if the spike finds QuickJS's in-process WASM isolation insufficient; it is not required for v1.

### 2. Deadline enforced host-side, not only via QuickJS interrupt
QuickJS's `shouldInterruptAfterDeadline` only stops the *interpreter* — an already-dispatched, awaited host promise (e.g. a slow LSP round trip) can keep running past the script's nominal budget and the run would never return. Required:
- Create one `AbortController` per script run at dispatch time; compute the absolute deadline once.
- Every host binding accepts/derives that signal and passes it into the same `signal` param already threaded through `grep`, `read`, `executeInspectV4`, and the LSP inspection functions (all already accept `AbortSignal`).
- Clamp any operation-specific internal timeout (e.g. LSP's own `timeoutMs`) to `min(operation default, remaining run budget)`.
- Once the deadline elapses, reject new dispatch immediately (don't even enter the host function body) and let in-flight calls race the abort signal to their own cancellation path.

**Follow-up (known gap, recorded 2026-09-13 — the requirement above is unchanged):** clamping an operation-specific internal timeout is unimplementable for the nav path without an `InspectV4Input` timeout channel: `NavigationParams` has no such field and `runNavOutcome` never forwards one, so the LSP navigation leg inside `executeInspectV4` still runs under its 5000ms default there, bounded only by the run signal. What script mode owns is clamped at its own boundary (injected-provider `timeoutMs`, diagnostics `waitMs`, pre-dispatch budget floor); threading a real per-call nav timeout through inspect remains an inspect-side change.

### 3. Host-side size and fan-out quotas, independent of the QuickJS heap limit
The QuickJS heap limit bounds guest-side memory, not host-side result payloads. Add, enforced in the host binding layer:
- Per-host-call result byte cap (serialize-then-measure before returning into the guest, truncate/error past cap rather than let a huge grep/read result blow guest heap on the JSON-bridge copy).
- Total-across-run returned bytes/resources cap.
- Final script return-value size cap (same truncation convention as existing `InspectV4Result` byte/line truncation).
- Category-specific call-count sub-budgets — `lsp.*` calls are markedly more expensive per call than `grep`/`read`, so the flat ~50 total must nest a tighter `lsp.*` sub-cap (spike measures the ratio).
- Max concurrent in-flight host operations (~5 provisional) — bounds `Promise.all` fan-out cost even though the *count* budget already bounds total calls.

### 4. Call counter must be atomic at function entry, before the first `await`
A naive `if (count < max) { count++; await doWork() }` has a check-then-increment race: `Promise.all([...100 calls])` all synchronously observe `count < max` before any of them awaits, and all 100 pass. The increment must happen synchronously in the same tick the binding function is entered — before any `await` — so budget enforcement is correct under concurrent dispatch by construction, not by locking.

### 5. Full audit surface stays visible in the outer result
The outer script result must carry a bounded call log — at minimum `{ op, args (redacted/truncated), canonicalPath or resourceId, status, elapsedMs }` per host call — so a single script invocation cannot hide what it actually touched behind one opaque return value. This is the mechanism that lets a reviewer or the calling model audit a multi-hop investigation after the fact, same intent as `queryResults` in grep's batch mode today. Only host calls that **completed successfully** contribute their envelope to the merged workspace evidence; failed/aborted/timed-out calls appear in the log (for visibility) but contribute no resources.

### 6. Stale-file evidence semantics — decided: last-completed-wins per resourceId
`resourceIdFor({kind, canonicalPath, range})` does not include a content hash, so two calls that observe the same file at different points in one script run (e.g. `read` early, then `read` again after a `grep` triggered a lazy index rebuild that raced a concurrent edit from another session) can produce the *same* `resourceId` with two different `fullFileSha256` values inside `InspectedResource`. Existing `buildBatchWorkspaceEvidence` dedupes with `if (seenResourceIds.has(id)) continue` — first-seen wins. That is wrong for script mode: keeping a stale hash only guarantees a downstream patch's freshness check fails against the *current* file when it would otherwise have succeeded against the resource observed later in the same run.
- Decision: when `buildBatchWorkspaceEvidence` runs in the generalized/script path, dedupe by **last-completed-wins** per `resourceId` (later entry in call-log completion order overwrites earlier), not first-wins.
- The existing `read({ paths: [...] })` call site keeps first-wins (its current, tested behavior) — this is a new option on the generalized function, not a change to the existing default.
- Document this as intentional: script mode does not attempt cross-call snapshot consistency; it optimizes for "the merged envelope reflects the most recent observation of each resource," and callers requiring stronger consistency should structure the script to read once and reuse that evidence, or accept that patch-time freshness re-verification is the actual backstop either way.

### 7. Grep compute/evidence separation — done
`executeInspectV4` (`src/inspect/inspect.ts`) was already a clean, exported, tool-wrapper-independent compute function — no change needed there.
Grep was not, but now is: `src/search/grep-tool.ts` exports `runGrepQueryWithEvidence(params: GrepQueryInput, cwd, opts, signal, sessionFilePath)`, which calls the (still module-private) `executeGrepQuery` then builds a per-call `WorkspaceEvidenceEnvelope` via `buildEvidence`, returning `{ result, evidence }`. It does not touch the resolver — publish stays exclusively in the tool wrapper's `execute()` closure. The registered `grep` tool's `execute()` now calls this same function for both its single-query and batch-query paths (batch still rebuilds a combined envelope across all queries' hits for correct multi-query range merging/inspectionId, matching prior behavior exactly). Verified byte-identical behavior via the existing grep test suite (74/74 passing) and a clean `tsc --noEmit`. The script host binding's `grep(pattern, opts)` calls `runGrepQueryWithEvidence` directly.

### 8. Non-workspace side effects — document, don't fake
Script mode does not mutate workspace source files (no `edit`/`write`/`patch` bindings exist). It is not side-effect-free in the broader sense:
- Graph/cache construction: `graph.*` bindings can trigger `ContextGraph` builds and LSP server starts on first use within a run, same as today's `inspect`/`grep` params that need them (`needsContextGraph`, `needsLspInspection`). This is derived, rebuildable I/O, not workspace mutation, but it is real work with real latency the first time.
- Reads performed via script host bindings bypass the ordinary context-hygiene / `file-read-cache.ts` recording path used by the top-level `read` tool, unless a future revision explicitly wires them in. For v1, this is accepted and documented rather than papered over with synthetic `read`-tool events — synthesizing fake read-cache entries for something that wasn't actually a top-level `read` call would misrepresent provenance.

## Risks and open questions
- Package pin **resolved**: `quickjs-emscripten@0.32.0` (root package, `justjake/quickjs-emscripten`), MIT, dist-tag `latest` confirmed directly against `registry.npmjs.org` on 2026-09-13. Size-sensitive alt if needed later: `quickjs-emscripten-core@0.32.0` + `@jitl/quickjs-wasmfile-release-sync@0.32.0` (1.3mb vs 9mb root). Async host-bridge for guest `await` works on the **default sync build** via `context.newPromise()` + `promise.resolve()` + `promise.settled.then(vm.runtime.executePendingJobs)` + `vm.resolvePromise()` — no asyncify needed for our case (script mode host bindings are called with normal `await` from guest `async` functions, not from guest sync-looking calls). The `RELEASE_ASYNC`/asyncify variant (`newAsyncContext`, `context.newAsyncifiedFunction`, `context.evalCodeAsync`) is only needed if a host binding must appear synchronous to guest code with no `await` — not our design, so **asyncify is not required for v1**; this simplifies §1's "keep the Asyncify bridge minimal" concern to "don't pull in asyncify at all." Confirmed API surface: `runtime.setInterruptHandler`/`shouldInterruptAfterDeadline` (§2 deadline), `runtime.setMemoryLimit`/`evalCode({ memoryLimitBytes })` (§3 heap), `vm.newFunction`/`vm.setProp` (host binding injection), `context.dispose()`/`runtime.dispose()` (§ context-per-run cleanup).
- Sub-second budget feasibility — spike-measured 2026-09-13 (`node scripts/spike-quickjs.mjs`, `quickjs-emscripten@0.32.0` exact): sync host round trip (runtime+context create, inject `add`, eval `add(2,3)`) ~8ms; async host bridge (100ms simulated host work, guest `await hostAsync()` via `vm.newPromise()` + `settled.then(executePendingJobs)` + `vm.resolvePromise()`, **no asyncify**) ~103ms total i.e. ~3ms bridge overhead — asyncify confirmed unnecessary for v1 as assumed. Infinite-loop interrupt fired at ~502ms against a 500ms `shouldInterruptAfterDeadline` (precise; `InternalError: interrupted`). Host-side `AbortController` (2s) bounded a 10s awaited host promise at ~2002ms while the interpreter interrupt was parked 30s out — §2's "host deadline wins" race behaves as designed. Memory limit tripped catchably (`InternalError: out of memory`, process survived) but took ~5.5s to trip at 8MB with a string-growth loop — OOM-trip latency depends on allocation pattern, so the wall-clock deadline (§2), not the heap limit, is the backstop that keeps worst-case runs bounded. Escape probe: `process`/`require`/`module` all `undefined` from guest; `eval`/`Function` exist as QuickJS builtins and the `Function`-constructor trick resolves to the *guest* `globalThis` (no host `process` reachable) — supports §1's plan to no-op `eval`/`Function` since they are present by default. Disposal: 20 create/eval/dispose cycles clean. Remaining benchmark gap (not covered by spike): real `lsp.*` latency under load — may still need a lower host-call cap or longer deadline when `lsp.*` ops are used, and the tighter `lsp.*` sub-budget (§3).
- Exact numeric budgets (byte caps, total-call cap, concurrent-call cap, per-category sub-caps) are provisional pending spike measurement — do not lock these as final until benchmarked.
- §7 grep extraction **done**: `runGrepQueryWithEvidence(params, cwd, opts, signal, sessionFilePath)` now exported from `src/search/grep-tool.ts`, returns `{ result, evidence }` with no resolver publish inside it. Verified: `npx vitest run` on the four grep test files (74 tests) passes, `tsc --noEmit` clean. Script mode's `grep()` host binding can call this directly.
